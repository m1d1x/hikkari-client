# AUTODEPLOY-ROADMAP

Инфраструктура «разворачивания протоколов на купленном VPS в 1 клик».
Двухконтурная: **B2C** (клиент вводит доступы к VPS → всё поднимается само с прогрессом/логами)
и **B2B** (админка для тех, кто разворачивает/администрирует много серверов).

Статус: черновик архитектуры. Дата: 2026-07-07.

---

## 0. TL;DR решения

- Провижининг делает **отдельный control-plane сервис (orchestrator)** на Go, а не сам Flutter-клиент.
  Клиент отдаёт `HOST_IP / USERNAME / PASSWORD` → orchestrator по SSH ставит протоколы на VPS,
  стримит структурированные логи обратно, в конце возвращает готовый **`Profile`-блок** (sing-box),
  который клиент кладёт в `profiles.json` через существующий FFI-контракт.
- Один и тот же orchestrator обслуживает и B2C, и B2B — B2B это просто расширенный UI + RBAC + инвентарь
  поверх той же job-модели.
- На VPS ставим **идемпотентный bootstrap** (Docker + docker-compose стек `sing-box server`), а не набор
  разрозненных bash-команд. Повторный запуск = сходимость к нужному состоянию, а не дубли.
- Логи двухуровневые: **dev-verbose** (полный поток шагов) и **prod-friendly** (прогресс-бар + фразочки),
  переключение — одна кнопка «показать детали». Кнопка «отправить в поддержку» шлёт support-bundle.

### Почему не SSH прямо из клиента

Соблазн: Flutter/Go-движок сам открывает SSH и ставит всё, backend не нужен. Отвергнуто:

- B2B (инвентарь, права, мониторинг парка) всё равно требует серверной части — построим её сразу.
- Пароль root от VPS не должен жить в приложении на устройстве; лучше кратко-живущий на orchestrator.
- Ретраи, докачка, идемпотентность, стрим логов нескольким наблюдателям — это серверная работа.
- Единая точка для будущего: провайдерские API (Hetzner/Vultr/DO) для «купить VPS не выходя из приложения».

> ⚠️ Открытый вопрос для решения на Phase 1: допускаем ли **опциональный** прямой-SSH-режим из движка
> для соло-энтузиастов без нашего backend (self-host orchestrator). См. §9.

## 1. Термины и границы

| Термин               | Что это                                                                                            |
| -------------------- | -------------------------------------------------------------------------------------------------- |
| **Client**           | Flutter-приложение Nekko (уже есть).                                                               |
| **Engine**           | Go-движок (`engine/core/*`), sing-box на стороне юзера. Потребитель `profiles.json`.               |
| **Orchestrator**     | Новый Go-сервис (control plane). SSH-провижининг, job-движок, стрим логов, выдача профилей.        |
| **Agent-node / VPS** | Купленный юзером сервер, куда ставим протоколы (egress).                                           |
| **Job**              | Один запуск деплоя на один VPS. Имеет шаги (steps), статус, лог-поток.                             |
| **Recipe**           | Декларативный рецепт: какой протокол + параметры → что сделать на VPS.                             |
| **Profile**          | То, что уже есть в движке: sing-box-блок сервера в `profiles.json`. **Финальный артефакт деплоя.** |

Протоколы v1 (совпадают с `Kind` движка):

- **VLESS + Reality/Vision** (`KindOutbound`) — приоритет №1, самый «чистый» под DPI.
- **Hysteria2** (`KindOutbound`) — быстрый UDP-фолбэк.
- **AmneziaWG** (`KindEndpoint`) — WG-совместимый, уже поддержан как endpoint.

## 2. Архитектура (высокоуровнево)

```
┌─────────────┐   HTTPS/WebSocket    ┌────────────────────┐    SSH     ┌──────────┐
│   Client    │◄────────────────────►│    Orchestrator    │──────────►│   VPS    │
│  (Flutter)  │   job API + log SSE  │  (Go control plane)│  password  │ agent-   │
│             │                      │                    │  /key      │ node     │
│ profiles.json◄── готовый Profile ──│  job engine        │           │ sing-box │
└─────────────┘                      │  recipe runner     │           │  server  │
      ▲                              │  log store         │           └──────────┘
      │ FFI {ok,data|error}          │  inventory (B2B)   │
┌─────┴───────┐                      │  auth / RBAC       │
│   Engine    │                      └─────────┬──────────┘
│ (sing-box)  │                                │
└─────────────┘                          ┌─────┴─────┐
                                         │ Postgres  │  jobs, nodes, tenants, users, audit
                                         │ + object  │  logs / support-bundles
                                         │  storage  │
                                         └───────────┘
```

Ключевые контракты:

- **Client ↔ Orchestrator**: REST для команд (`POST /deploy`, `GET /jobs/:id`), **SSE/WebSocket** для лог-стрима.
- **Orchestrator ↔ VPS**: SSH (пароль на первом заходе → сразу подменяем на ephemeral SSH-ключ).
- **Orchestrator → Client → Engine**: готовый `Profile` JSON, клиент вызывает существующий FFI-метод
  добавления профиля (нужно добавить `Core.AddProfile` в `api/methods.go`, см. §6).

## 3. Job-модель и стейт-машина деплоя

Один Job = один VPS. Шаги идемпотентны, каждый шаг эмитит структурированные лог-события.

```
CREATED
  → PREFLIGHT      (пинг, SSH-коннект, sudo/root, ОС/арх, свободные порты, дата/время)
  → HARDEN         (ephemeral SSH-ключ, отключить пароль-SSH опц., ufw/iptables baseline)
  → INSTALL_BASE   (docker + compose plugin, зависимости; идемпотентно)
  → CONFIGURE      (сгенерить ключи протокола: reality keypair, hy2 pwd, wg keys; конфиг sing-box)
  → DEPLOY         (docker compose up -d стек sing-box server; открыть порт в fw)
  → VERIFY         (health: порт слушает; тест-хендшейк изнутри; egress-IP; TLS/Reality отвечает)
  → EMIT_PROFILE   (собрать Profile-блок под клиента, вернуть)
  → DONE
  ↘ FAILED(step, reason, remediation?)   — на любом шаге; с диагностикой и hint'ом
```

Свойства:

- **Идемпотентность**: повторный Job на тот же VPS не ломает — сверяет состояние и доводит.
- **Ретраи**: транзиентные ошибки (сеть, apt lock) — авто-ретрай с backoff; фатальные — стоп + причина.
- **Rollback (мягкий)**: при FAILED оставляем VPS в диагностируемом виде, не «наполовину»; кнопка
  «повторить с этого шага» и «снести всё и начать заново».
- **Каждый шаг** = { `id`, `title`, `status`, `startedAt`, `finishedAt`, `logRef` }.

### Модель лог-события (структурно, JSON-lines)

```json
{ "ts": "...", "jobId": "...", "step": "DEPLOY", "level": "info|warn|error",
  "code": "docker.pull.progress", "msg": "human text",
  "public": "Поднимаем протоколы…",   // prod-friendly фраза (может быть null)
  "detail": { ... } }
```

- `msg` — dev-уровень (полный текст, stderr команды и т.п.).
- `public` — то, что видит обычный юзер (фразочка/этап). Маппинг `code → public` — в одном месте.
- `level=error` всегда сопровождается `code`, чтобы был actionable hint и текст для саппорта.

## 4. Провижининг на VPS (recipe runner)

### 4.1 Механизм

- Транспорт: **SSH** (`golang.org/x/crypto/ssh`). Первый заход по паролю → генерим ed25519 keypair,
  кладём паблик в `authorized_keys`, дальше только по ключу. Пароль в памяти orchestrator живёт секунды,
  на диск не пишется (только в секрет-хранилище зашифрованным, если юзер выбрал «запомнить VPS»).
- Исполнение: заливаем **идемпотентный bootstrap-пакет** (bash + compose-файлы + шаблоны), запускаем,
  парсим structured output (маркерные строки `##NEKKO step=... status=...`).
- Состояние на VPS: `/opt/nekko/` — compose-файлы, конфиги, сгенерённые ключи, `state.json`.

### 4.2 Рецепты (шаблоны protocol → config)

Каждый протокол — Go-шаблон, дающий пару **(server-config для VPS, client-Profile-блок)**:

- **VLESS+Reality**: генерим x25519 keypair (reality), shortId, выбираем `serverName` (dest-камуфляж,
  напр. `www.microsoft.com`), порт 443. Server → sing-box `vless` inbound с `tls.reality`.
  Client → `KindOutbound` VLESS с `reality.public_key`, `short_id`, `utls.fingerprint`.
- **Hysteria2**: генерим пароль, self-signed или ACME по домену (опц.), порт UDP. Server → `hysteria2` inbound.
  Client → `KindOutbound` hysteria2.
- **AmneziaWG**: генерим wg keypair + obfs-параметры (Jc/Jmin/Jmax/S1/S2/H1..H4). Server → wg-easy-like
  или sing-box-endpoint. Client → `KindEndpoint`.

> Секреты (reality private key, hy2 password, wg private) генерятся на orchestrator, **приватная часть
> уходит на VPS**, в client-Profile идёт только то, что нужно клиенту (public_key/short_id/password).

### 4.3 Подход к упаковке

- v1: **docker compose** стек `ghcr.io/sagernet/sing-box` server + tiny sidecar для health/metrics.
  Плюс: одна артефактная граница, легко апдейтить/сносить, чисто.
- Firewall: `ufw`/`iptables` — открываем только нужные порты, остальное режем.
- (Отложено) вариант «bare systemd без Docker» для дешёвых/урезанных VPS — Phase 4.

## 5. Клиентский UX (B2C)

### 5.1 Экран «Развернуть свой сервер»

Три поля (как просил юзер): `HOST_IP`, `USERNAME (root)`, `PASSWORD`. Плюс:

- выбор протокола (по умолчанию VLESS+Reality, «рекомендуем»), опц. домен для ACME.
- кнопка **Развернуть** → создаёт Job, открывает экран прогресса.

### 5.2 Экран прогресса

- **Prod-режим (по умолчанию)**: крупный прогресс-бар по шагам + сменяющиеся фразочки
  («Проверяем сервер…», «Ставим протоколы…», «Наводим чистоту…», «Почти готово…»),
  тянутся из `public`-поля лог-событий.
- Кнопка **«Показать детали»** → раскрывает dev-лог (полный поток, моноширинный, автоскролл, фильтр по level).
- На **FAILED**:
  - показываем человекочитаемую причину + hint (из `code`),
  - кнопка **«Разобраться самому»** (открыть детальный лог + doc-ссылку по коду ошибки),
  - кнопка **«Написать в поддержку»** → формирует **support-bundle** (job-лог, шаги, коды, редакция
    секретов) и открывает предзаполненный тикет/чат с прикреплённым bundle.
- На **DONE**: «Сервер готов», профиль автоматически добавлен и выбран; кнопка «Проверить чистоту»
  (переиспользуем `ServerCleanliness`).

### 5.3 Приватность логов

- Секреты (пароль VPS, приватные ключи) **никогда** не попадают в лог/bundle — редактор на уровне
  лог-эмиттера (allowlist полей, маскирование по regex ключей).

## 6. Изменения в Engine / FFI (что дописать в наш код)

- `api/methods.go`: `Core.AddProfile(profileJSON string) error` и `Core.RemoveProfile(name string)` —
  чтобы клиент мог программно вкинуть выданный orchestrator Profile в `profiles.json`.
  (Сейчас профили, судя по `profile.go`, есть, но нужен явный публичный метод добавления через диспетчер.)
- `api/dispatch.go`: зарегистрировать новые методы в JSON-роутере (тот же конверт `{ok,data|error}`).
- (Опц.) `Core.ImportProfileFromDeploy(...)` если формат от orchestrator отличается от on-disk `Profile`
  — но лучше сразу отдавать канонический `Profile` JSON, чтобы конверсии не было.
- Клиент (`app/lib/core/nekkobox_core.dart` + `state/app_state.dart`): методы вызова orchestrator API
  и обёртка над FFI-добавлением профиля.

> Важно: orchestrator генерит Profile **строго в формате `profile.Profile`** (`name/label/kind/config`),
> чтобы `RebuildActive` и селектор `proxy` подхватили сервер без спец-обработки.

## 7. B2B / Админка

Та же job-модель + orchestrator, сверху — многопользовательский слой.

### 7.1 Сущности

- **Tenant** (организация/реселлер) → **Users** (роли) → **Nodes** (парк VPS) → **Jobs** (история деплоев).
- **Роли/RBAC**: owner / admin / operator / viewer. Права на: деплой, пересоздание, удаление, выдача
  клиентских профилей/ключей, просмотр логов, биллинг.

### 7.2 Функции админки

- **Инвентарь серверов**: список нод, статус (health/uptime/чистота — переиспользуем движковые чекеры,
  но серверную их версию), нагрузка, кол-во клиентов, срок/биллинг VPS.
- **Массовый деплой**: развернуть N нод пачкой, шаблоны конфигов, теги/группы.
- **Управление клиентами/ключами**: выдавать sub-ссылки/профили конечным пользователям, ротировать,
  ревокать; лимиты по трафику/устройствам.
- **Мониторинг**: агрегированные метрики парка, алерты (нода упала, порт закрылся, IP забанен CF).
- **Аудит**: кто что задеплоил/удалил/выдал — журнал.
- **Биллing hooks** (Phase 4): интеграция с провайдерами VPS (Hetzner/Vultr/DO API) — «купить и развернуть».

### 7.3 UI B2B

- Отдельная web-админка (или расширенный раздел в приложении). React/веб — вероятно отдельный фронт,
  т.к. desktop-heavy. Решить на Phase 3.

## 8. Безопасность (сквозная)

- Пароль root VPS: transient, в память orchestrator, ephemeral-ключ на замену; «запомнить» → шифрованно
  в KMS/секрет-сторе, не в БД открыто.
- Секреты протоколов генерятся серверно, приватная часть только на VPS; редакция в логах/бандлах.
- Orchestrator API: аутентификация клиента (device token / аккаунт), rate-limit, tenant-изоляция.
- SSH host-key pinning: при первом заходе фиксируем host key, при смене — предупреждение (MITM-защита).
- Отдельный least-privileged системный юзер на VPS для стека (не гоняем всё под root после bootstrap).
- Аудит и трассируемость всех действий.

## 11. Что переиспользуем из уже готового

- **Формат `Profile`** (`engine/core/profile/profile.go`) — финальный артефакт деплоя, без конверсий.
- **FFI-конверт** `{ok,data|error}` (`api/dispatch.go`) — тот же контракт для новых методов.
- **Cleanliness-чекер** (`engine/core/cleanliness/`) — верификация egress после деплоя (клиентская),
  плюс серверная версия для B2B-мониторинга. Нюанс фидельности JA3/JA4 см. память `[[server-cleanliness]]`.
- **Health/uptime** (`engine/core/health`, `uptime`) — паттерн фонового чекера для мониторинга нод.
- **bench/** — офлайн-перебор хостингов: пригодится как «оценщик пригодности VPS» перед массовым деплоем.
